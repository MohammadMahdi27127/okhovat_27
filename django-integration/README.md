# مدل‌های پیشنهادی اخوت برای safa27
هدف Django 5.2 و PostgreSQL است. این بسته یک اپلیکیشن یا migration آمادهٔ اجرا برای دیتابیس موجود نیست. محتوای کامل پیشنهادی در core/models.py است. مدل‌های قبلی فقط از روی نام‌ها بازسازی شده‌اند. پیش از ادغام، فیلدهای فعلی، نوع کلیدهای اصلی، نام جدول‌ها، روابط، managerها، app label و migrationهای فعلی مرجع هستند. مدل کاربر موجود و AUTH_USER_MODEL را حفظ کنید. فایل اعتبارسنج و توابع default که در migrationها ثبت می‌شوند باید در مسیر import پایدار بمانند.

## فرض‌های قابل تغییر
- هر عضو حداکثر یک حلقه و ممکن است چند کارگروه داشته باشد. سرحلقه از اعضای همان حلقه است. برای سقف دو سرحلقه، هنگام انتساب، ردیف حلقه را در تراکنش قفل و ظرفیت را بررسی کنید.
- bale_id در این طرح chat_id عددی گفت‌وگوی خصوصی بات است. اگر دادهٔ واقعی نام کاربری است، آن را جدا نگه دارید.
- نداشتن درصد حضور با صفر درصد متفاوت است. coach_score خام ذخیره می‌شود؛ ضریب ۲ مربی و میانگین درصد حضور را هنگام محاسبهٔ رتبه اعمال کنید.
- مصوبه در این مرجع برای یک حلقه یا کارگروه است. اگر مدل فعلی مصوبات فردی یا عمومی هم دارد، قید هدف را مطابق آن گسترش دهید.
- UserInteraction.session_id یک UUID تصادفی مخصوص آمار است. از شناسهٔ نشست ورود یا مقدار کوکی استفاده نکنید. فقط داده‌های مجاز و محدود را از کلاینت بپذیرید؛ متن پیام، محتوای چت AI و اطلاعات ورود را وارد metadata نکنید. JSONField برای PostgreSQL ستون jsonb ایجاد می‌کند.
- یک ReelView یک رویداد تماشا است؛ تماشای تکراری می‌تواند رویداد جدا داشته باشد. لایک و پیشنهاد هر کاربر برای یک پست یکتا هستند. شمارندهٔ پسند مستقل نگهداری نمی‌شود.
- فهرست ترند بر اساس وجود recommendation روی پست منتشرشده است. برای جلوگیری از ردیف تکراری از Exists استفاده کنید. در رتبهٔ حلقه، فقط likes با counts_for_ring=True روی پست برنامهٔ حذف‌نشده جمع شوند؛ set_post_like در social_services.py این مقدار را در زمان لایک تعیین می‌کند.
- فیلد published_at خالی یعنی پیش‌نویس. کوئری عمومی کارت‌ها و ریلز باید published_at__lte=timezone.now() را اعمال کند. فید باید deleted_at__isnull=True را فیلتر کند.
- مجوز ساخت پست مربی، تعلق حاضران به حلقه، تطبیق نویسنده با صاحب گزارش رشد، مدیریت کارگروه و تکمیل مصوبه در endpoint بررسی می‌شوند. برای اعضای معلق، همهٔ عملیات محافظت‌شده در هر درخواست باید وضعیت فعلی را بررسی کنند. مدل به تنهایی دسترسی HTTP را کنترل نمی‌کند. انتشار خلاصهٔ رشد با گزارش در یک تراکنش و با یک Post برای هر گزارش انجام شود. فقط عنوان مهارت در خلاصهٔ عمومی درج شود.
- قبل از ذخیره در API، full_clean یا اعتبارسنجی معادل انجام دهید. محدودیت ۱۰ مگابایت را در لایهٔ دریافت فایل نیز اعمال کنید. فایل‌های خصوصی از URL عمومی ارائه نشوند.

## ترتیب migration پیشنهادی برای دیتابیس موجود
1. خروجی showmigrations core و مدل اصلی را تطبیق دهید. مدل‌های قدیمی را حذف و از نو ایجاد نکنید. از دیتابیس بکاپ بگیرید و ابتدا روی کپی اجرا کنید.
2. بعد از آخرین migration واقعی core، فیلدهای جدید User و تغییرات تأییدشدهٔ مدل‌های موجود را اضافه کنید. برای داده‌های نامعلوم از null و برای نقش‌های تازه از False استفاده کنید. عضویت تاریخی یا نمره را حدس نزنید.
3. جدول‌های مستقل Post، Reel، LandingContent، UserInteraction و AIUsageLog را ایجاد کنید. وابستگی Post به جلسه و رشد فردی را حفظ کنید.
4. PostLike، PostComment، PostRecommendation، ReelLike، ReelComment، ReelView و جدول‌های واسط جدید را اضافه کنید. اگر از سامانه دیگری داده وارد می‌کنید، برای تخصیص روابط از RunPython با apps.get_model و نقشهٔ کلیدهای واقعی استفاده کنید.
5. پیش از سخت‌گیری روی دادهٔ قدیمی، رکوردهای تکراری، سرحلقهٔ بدون حلقه، درصد نامعتبر، مصوبهٔ بدون هدف و نشست‌های قبلی را بررسی کنید. قیود یکتایی و CheckConstraintها و شاخص‌ها را پس از پاک‌سازی اضافه کنید. برای جدول‌های تازه و خالی، ساخت قید هم‌زمان با جدول کافی است.
6. migrationهای django.contrib.sessions باید اعمال شده باشند. تاریخ انقضای هفت‌روزهٔ ثابت را هنگام ورود جدید ثبت کنید. سیاست انتقال نشست‌های قدیمی را بر اساس مدل ورود قبلی مشخص کنید.

پس از ادغام، در پروژهٔ واقعی:

```sh
python manage.py check
python manage.py showmigrations core
python manage.py makemigrations core --dry-run --verbosity 3
python manage.py makemigrations core
python manage.py migrate --plan
python manage.py migrate
python manage.py makemigrations --check --dry-run
```

این دستورها لزوماً پنج فایل migration تولید نمی‌کنند. برای انتقال دیتابیس دارای داده، عملیات تولیدشده را به مراحل بالا تقسیم و dependencies را به آخرین migration واقعی وصل کنید. اگر خروجی ناخواسته شامل DeleteModel، RemoveField یا ایجاد دوبارهٔ جدول موجود بود، قبل از migrate اختلاف را حل کنید.

## کش و ورود
تنظیمات cache_settings.py را ادغام کنید. بستهٔ redis برای RedisCache و درایور psycopg مناسب نسخهٔ نصب‌شدهٔ Django لازم است. REDIS_DATA_URL و REDIS_SESSION_URL را در محیط سرور تنظیم کنید. برای جداسازی عملیاتی از دو دیتابیس منطقی مجزا یا دو instance استفاده کنید. TTL داده از زمان نوشتن هر کلید ۹۰۰ ثانیه است. پاک‌سازی سراسری یا FLUSHALL زمان‌بندی نکنید.

Redis کش سمت سرور است. برای مرورگر روی پاسخ عمومی یکسان برای همه، cache_control(public=True, max_age=900) مناسب است. برای پروفایل، گزارش‌ها، فرم ورود، مسیرهای شخصی و پاسخ حاوی اطلاعات نشست از never_cache یا Cache-Control: private, no-store استفاده کنید. CacheMiddleware سراسری را روی پاسخ‌های شخصی فعال نکنید. برای تغییراتی مثل حذف پست، کلیدهای مرتبط سرور را هنگام موفقیت تراکنش با transaction.on_commit باطل کنید.

django.contrib.sessions و SessionMiddleware و AuthenticationMiddleware باید در تنظیمات پروژه باشند. در همهٔ مسیرهای ورود موفق، پس از authenticate از core.session_policy.finish_login استفاده کنید؛ همین مهلت باید در ورود پس از بازیابی رمز اعمال شود. درخواست عادی نباید set_expiry را مجدداً اجرا کند. cached_db نسخهٔ پشتیبان نشست را در PostgreSQL نگه می‌دارد. با خروج دستی از django.contrib.auth.logout استفاده کنید. تنظیم Secure برای محیط HTTPS است.
